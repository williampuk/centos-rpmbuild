Pinning a Live ISO to kernel 5.14.0-645.el9

A Linux-newbie-friendly deep dive into what “pin the kernel” really means, why pinning source code is not enough, how the exact CentOS binary RPM build is selected, and how the final ISO proves the correct kernel was installed.

1. The requirement

The normal CentOS Stream 9 build follows the current Stream kernel. That is normally desirable, but it does not satisfy software or hardware that requires one precise ABI/kernel build.

Hard requirement:
uname -r should correspond to 5.14.0-645.el9.x86_64, and the development tree used to compile external modules must come from the matching kernel-devel-5.14.0-645.el9 package.

This repository therefore keeps the rolling image in live-iso/ and creates a separate compatibility variant in:

live-iso-5.14.0-645.el9/

2. Three different things people call “the kernel version”

Linux source commit

A Git commit in a kernel source repository. It identifies source text. It does not by itself identify the exact RPM packaging, configuration, patches, build flags, signing, or binary artifacts installed by CentOS.

CentOS kernel RPM build

A particular packaged build such as kernel-5.14.0-645.el9. This is what DNF and KIWI install. For this project, this is the important pin.

Whole OS snapshot

The exact versions of every RPM and every repository used by the system. Pinning only the kernel does not freeze glibc, curl, NetworkManager, GCC, or the rest of Stream 9.

KIWI recipe commit

The exact CentOS Alternative Images description used to assemble the Live image. We record it for traceability, but this kernel-pinned variant still follows the moving c9s recipe unless you later decide to freeze the whole build.

Main lesson: pinning a source Git commit is not enough to guarantee the binary kernel that appears inside an RPM-based Linux image.

3. NVR and NEVRA

RPM ecosystems identify packages using pieces of metadata. Two useful acronyms are:

NameMeaningExample
NVRName + Version + Releasekernel-5.14.0-645.el9
NEVRAName + Epoch + Version + Release + Architecturekernel-core-0:5.14.0-645.el9.x86_64 (conceptually)

The project pins:

KERNEL_NVR=kernel-5.14.0-645.el9
KERNEL_BUILD_ID=91148
KERNEL_VERSION=5.14.0
KERNEL_RELEASE=645.el9
TARGET_ARCH=x86_64

Those values live in config.env, so the compatibility target is obvious rather than hidden inside a long shell command.

4. What is Koji?

Koji is the build system used to build and track RPM artifacts. Think of it as a factory database:

kernel source + spec + patches + build configuration │ ▼ Koji build │ build ID 91148 │ ▼ kernel-5.14.0-645.el9 │ ┌────────────────┼─────────────────────┐ ▼ ▼ ▼ kernel-core kernel-devel kernel-modules... .rpm .rpm .rpm

The build does not merely trust our text configuration. A standalone verify-koji.py helper is mounted read-only into the build container, queries the public Koji XML-RPC API, and requires:

build ID 91148
        │
        └── NVR == kernel-5.14.0-645.el9

It then asks Koji for the RPM list and checks that all required x86_64 package names exist in that build.

Why keep both NVR and build ID? They are two independent identifiers that make accidental misconfiguration easier to detect. The build aborts if they disagree.

6. Why repository priority is the key

CentOS Stream is a moving stream. Today its normal repositories may contain kernels much newer than 5.14.0-645.el9.

If the build simply asks for:

kernel
kernel-devel

DNF normally chooses the current available versions. That defeats the compatibility requirement.

Instead, the script creates a local RPM-MD repository and passes it to KIWI:

--add-repo="dir:///pinned-kernel-repo,rpm-md,pinned-kernel,1,..."

With DNF-style priority semantics, a lower numeric priority value is stronger. So the pinned repository is allowed to win for package names that also exist in ordinary Stream 9 repositories.

pinned-kernel repo (priority 1) kernel-core 5.14.0-645.el9 │ │ wins package choice ▼ normal Stream repo (lower priority) kernel-core 5.14.0-newer.el9

Everything not present in the small pinned repository still comes from the ordinary repositories.

7. Why kernel-devel must match the running kernel

External kernel modules are normally compiled against a kernel build tree referenced by:

/lib/modules/$(uname -r)/build

That link/tree is supplied by the matching kernel-devel package.

uname -r 5.14.0-645.el9.x86_64 │ ▼ /lib/modules/5.14.0-645.el9.x86_64/build │ ▼ kernel-devel-5.14.0-645.el9.x86_64 │ ▼ vendor driver source │ ▼ make / DKMS / installer │ ▼ driver.ko

A mismatch such as a running -645 kernel with kernel-devel -700 can cause module builds to fail or compile against the wrong ABI/configuration.

That is why this project pins the runtime kernel and kernel-devel together as one family.

8. The final image is verified, not assumed

After KIWI builds the image, it emits a normalized package manifest. For RPM images, each line has this shape:

name|epoch|version|release|arch|disturl|license

The script finds the generated *.packages file and requires every pinned component to report:

version = 5.14.0
release = 645.el9
arch    = x86_64

It also requires exactly one kernel-core record. This catches the dangerous case where the required kernel is present but a newer second kernel also entered the image and might become the boot default.

9. Kernel-pinned does not mean fully reproducible

This design intentionally answers a narrow hard requirement: keep the kernel at 5.14.0-645.el9.

FROZEN ────── kernel kernel-core kernel-modules-core kernel-modules kernel-modules-extra kernel-devel kernel-headers MOVING WITH STREAM 9 / EPEL ─────────────────────────── glibc gcc bash curl NetworkManager xorriso rpmlint ... KIWI c9s recipe (commit recorded per build)

Therefore, an ISO built six months later can contain the same kernel but newer user-space packages.

What would “freeze the whole OS” require?

  • Pin the exact CentOS AltImages Git commit rather than following c9s.
  • Use immutable CentOS repository snapshots/compose URLs rather than current Stream mirrors.
  • Snapshot/pin EPEL too.
  • Pin the build container by content digest.
  • Record or pin the KIWI version.
  • Control timestamps and other nondeterministic build inputs if byte-for-byte reproducibility is required.

That is a different—and much broader—engineering goal.

10. The security tradeoff

Pinning an old kernel means intentionally not receiving later kernel security fixes and bug fixes.

This can be justified when a vendor driver, appliance certification, or hardware qualification mandates an exact kernel. But the exception should be documented and periodically reviewed.

If the compatibility constraint disappears, prefer the ordinary rolling live-iso/ build.

11. Project layout

live-iso-5.14.0-645.el9/ ├── build.sh │ └── complete build + validation pipeline ├── verify-koji.py │ └── standalone Koji verifier mounted into the build container ├── config.env │ └── kernel NVR, Koji build ID, architecture, Koji endpoints ├── kernel-rpms.txt │ └── exact kernel package names that must be pinned ├── packages.txt │ └── non-kernel RPM/build/network/DVD tools ├── README.md │ └── operating instructions └── build-guide.html └── this tutorial

Why separate kernel-rpms.txt from packages.txt?

Kernel packages have a different trust/selection rule. They must come from the verified historical Koji build. Ordinary tools should continue resolving from standard Stream/EPEL repositories. Keeping the lists separate makes this security boundary visible.

12. CI and releases

The pinned variant has dedicated workflows, so changes do not interfere with the normal Stream 9 image:

.github/workflows/
├── build-live-iso-kernel-5.14.0-645-el9.yml
└── release-live-iso-kernel-5.14.0-645-el9.yml

The release workflow intentionally uses a separate tag namespace:

kernel-5.14.0-645.el9-v0.0.1
kernel-5.14.0-645.el9-v0.0.2-beta

This avoids triggering the ordinary rolling image's v* release workflow.

13. Linux-newbie glossary

Kernel

The privileged core of Linux. It manages CPU scheduling, memory, devices, filesystems, networking, and the boundary between hardware/kernel space and normal programs.

Kernel module

A loadable piece of kernel code, often a driver. Module files normally end in .ko.

kernel-devel

The package containing the build tree, generated headers, Makefiles, and configuration needed to compile external modules for a specific packaged kernel.

Koji

An RPM build and tracking system. A Koji build has an ID and produces one or more RPM artifacts.

RPM

The package format used by CentOS/RHEL/Fedora-family distributions. An RPM contains files plus metadata such as name, version, release, architecture, dependencies, and scripts.

NVR / NEVRA

NVR means Name-Version-Release. NEVRA additionally includes Epoch and Architecture. These are more precise package identities than a friendly package name such as “kernel”.

Repository

A collection of packages plus metadata that allows a package manager such as DNF to discover versions and resolve dependencies.

Repository priority

A rule that lets packages from one repository take precedence over same-named packages from another repository. This build gives the pinned local kernel repository the strongest priority.

createrepo_c

A utility that generates RPM-MD repository metadata around a directory of RPM files, turning that directory into something DNF/KIWI can consume as a repository.

KIWI *.packages

A normalized inventory generated by KIWI from the final image's package database. It is used here as the post-build proof of the actual kernel versions installed.
