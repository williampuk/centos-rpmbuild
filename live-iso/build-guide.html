1. What we wanted to build

The goal was not merely â€œinstall a few packages.â€ We wanted a bootable Live ISO of CentOS Stream 10 that already contains a complete basic RPM-building environment:

The result should be buildable automatically in GitHub Actions, so the repository itself becomes the recipe for producing the ISO.

End result: a GitHub Actions run produces a bootable .iso, a SHA256SUMS file, and UPSTREAM_COMMIT.txt recording exactly which CentOS image-description revision was used.

2. The core concepts first

What is a Live ISO?

An ISO is a filesystem image traditionally associated with optical discs. A Live ISO contains enough of an operating system to boot and run directly from the media without first installing it onto the machine's main disk.

What is KIWI?

KIWI NG is an operating-system image builder. You give it an image description plus package repositories; it creates a Linux filesystem tree and then packages that tree into an output format such as an ISO.

What is the build container?

The CentOS Stream 10 Docker container is only the factory in which KIWI runs. It is not the final Live OS. The final Live OS is independently assembled by KIWI from CentOS repositories and the CentOS image description.

Why GitHub Actions?

GitHub gives us an ephemeral Linux machine called a runner. Every run starts clean, checks out our repository, builds the image, and uploads the output as an artifact.

A useful mental model
GitHub runner = rented workshop
CentOS container = controlled workbench
KIWI = image-building machine
CentOS KIWI description = blueprint
RPM repositories = parts warehouse
packages.txt = our extra parts list
ISO = finished product

3. Final architecture

Very important distinction: Docker is not being used to â€œturn a container into an ISO.â€ Docker only gives KIWI a predictable CentOS Stream 10 environment in which to do its work.

4. The build pipeline, step by step

1
GitHub allocates an Ubuntu runner.
This is a temporary VM. Nothing from a previous run should be assumed to exist.
2
The repository is checked out.
Our workflow gets live-iso/build.sh, packages.txt, and the rest of the project.
3
Some preinstalled runner software is deleted.
Android, GHC, and .NET directories are removed to free tens of GB for image building.
4
build.sh clones the CentOS Alternative Images recipe.
It checks out the c10s branch and records its exact Git commit SHA.
5
A privileged CentOS Stream 10 container starts.
The upstream recipe directory, output directory, package list, and host /dev are mounted into it.
6
KIWI is installed inside the container.
The container is disposable, so installing build dependencies inside it keeps the GitHub host cleaner.
7
The package list becomes KIWI CLI arguments.
rpm-build becomes --add-package=rpm-build, etc.
8
KIWI builds MIN-Live.
KIWI resolves packages, constructs the future root filesystem, adds the boot infrastructure, then creates the final ISO.
9
The ISO is checksummed and uploaded.
GitHub Actions exposes the result as a downloadable workflow artifact.

5. What build.sh is really doing

Fail fast

set -euo pipefail
FlagMeaning
-eExit when a command fails instead of blindly continuing.
-uTreat an unset variable as an error.
pipefailIf one command in a pipeline fails, the pipeline is considered failed.

Default values that can still be overridden

UPSTREAM_BRANCH="${UPSTREAM_BRANCH:-c10s}"
KIWI_PROFILE="${KIWI_PROFILE:-MIN-Live}"

The ${VAR:-default} shell syntax means: â€œuse the environment variable if one was supplied; otherwise use this default.â€ This makes the script configurable without editing it.

Why record the upstream commit?

git -C "${UPSTREAM_DIR}" rev-parse HEAD \
  > "${OUT_DIR}/UPSTREAM_COMMIT.txt"

We intentionally track a moving branch (c10s). That means two builds performed months apart might use different CentOS image descriptions. Recording the Git commit gives us a trace of what â€œupstreamâ€ actually meant for a particular build.

The most important Docker command

docker run --rm --privileged \
  -v /dev:/dev \
  -v "${UPSTREAM_DIR}:/kiwi:rw" \
  -v "${OUT_DIR}:/out:rw" \
  -v "${SCRIPT_DIR}/packages.txt:/packages.txt:ro" \
  -e "KIWI_PROFILE=${KIWI_PROFILE}" \
  quay.io/centos/centos:stream10 \
  bash ...
--rm
Delete the temporary container when it exits.
--privileged
Give the container broad device/kernel capabilities needed by low-level image-building operations.
-v /dev:/dev
Expose host device nodes to the build container. Image construction may need loop/device-mapper style operations.
:rw
Read-write bind mount.
:ro
Read-only bind mount; ideal for our package-list input.
-e
Pass an environment variable into the container.

Turning a text file into KIWI arguments

mapfile -t packages < <(
  grep -Ev "^[[:space:]]*(#|$)" /packages.txt
)

package_args=()
for package in "${packages[@]}"; do
  package_args+=(--add-package="${package}")
done

This is a nice shell pattern. Blank lines and comments are filtered out, then every real line becomes one array element. We deliberately use a Bash array rather than constructing a giant command string, because arrays preserve argument boundaries correctly.

Why the final approach is robust: we customize through KIWI's documented public CLI instead of reaching into CentOS's internal XML layout. That is an API-boundary lesson: prefer supported interfaces over editing implementation details.

6. The GitHub Actions workflow explained

jobs:
  build-live-iso:
    runs-on: ubuntu-24.04
    timeout-minutes: 120

A job is one unit of work running on one runner. Here the runner is Ubuntu 24.04 and GitHub will stop it after two hours.

Why free disk space?

Image creation temporarily needs much more storage than the finished ISO. KIWI first constructs an entire filesystem tree, maintains caches and package downloads, and then emits the compressed image.

sudo rm -rf /usr/local/lib/android /opt/ghc /usr/share/dotnet
df -h
On the successful direction of our experiments, freeing runner disk space was not cosmetic. OS-image builds are fundamentally disk-heavy workloads.

Why invoke the script with bash?

run: bash ./live-iso/build.sh

This does not require the file to have Unix executable permission. It explicitly asks Bash to read and run the file.

Uploading the finished product

uses: actions/upload-artifact@v4
with:
  name: centos-stream-10-rpm-builder-live
  path: |
    live-iso/out/*.iso
    live-iso/out/SHA256SUMS
    live-iso/out/UPSTREAM_COMMIT.txt

A GitHub Actions artifact is simply a file bundle preserved after the ephemeral runner disappears.

Where our extra RPM packages fit

The --add-package option says: â€œtake the official description and additionally install this package into the image.â€ It can be specified repeatedly. This is exactly what we want because our desired difference from the official MIN Live image is primarily package selection.

Why EPEL and CRB show up

CentOS BaseOS/AppStream do not necessarily contain every development utility. EPEL (Extra Packages for Enterprise Linux) provides additional packages, while CRB contains development-oriented dependencies needed by some packages. The build container enables them so KIWI and the image recipe can resolve required software.

8. The trial-and-error timeline â€” and what each failure taught us

Failure 1 â€” Permission denied

./live-iso/build.sh: Permission denied
exit code 126

Cause: the script did not have the executable Git mode bit.

Fix: run it as bash ./live-iso/build.sh.

Lesson: a shell script is just a text file. The shebang does not magically make it executable; Unix permissions still matter. Explicitly invoking the interpreter bypasses that requirement.

Failure 2 â€” â€œNo MIN-Live profileâ€ from the first upstream source

Cause: we initially used a GitLab migration target that did not contain the complete live-image recipe content we expected.

Fix: follow the CentOS Alternative Images documentation and clone the Pagure repository.

Lesson: â€œofficial-looking repositoryâ€ is not the same thing as â€œcurrently authoritative build input.â€ When upstream projects migrate hosting, documentation and repository state can temporarily diverge.

Failure 3 â€” shallow clone rejected

fatal: dumb http transport does not support shallow capabilities

Cause: Pagure's Git endpoint did not support the protocol features required by --depth 1.

Fix: perform a normal branch clone without shallow history.

Lesson: Git is a protocol ecosystem, not just the git command. Different servers/transports support different capabilities.

Failure 4 â€” our profile parser found no profiles

Cause: we assumed profiles had to appear in the root config.xml in a particular XML shape.

Fix: stop trying to reverse-engineer the current internal XML representation.

Lesson: whenever a project exposes a documented CLI/API, use it instead of building logic around its private file organization.

Failure 5 â€” Could not find </image>

Cause: the current CentOS image recipe is componentized; our script assumed a classic monolithic XML document and tried to inject XML text before a closing </image> tag.

Fix: remove XML rewriting completely.

Lesson: text surgery on structured configuration is fragile. Even using an XML parser would still unnecessarily couple us to the description's internal structure.

Final design â€” use KIWI's own override interface

--add-package=rpm-build
--add-package=rpmdevtools
...

Why it is better: it expresses exactly what we mean â€” â€œbuild the official profile, plus these packagesâ€ â€” without mutating upstream configuration.
